# CHIGIRI Beauty

> 買う前に、今あるものをつなぐ。

手持ちの化粧品を再編成し、本当に不足している商品だけを理由付きで提案する**美容ルーティン最適化 AI**。
チャットで話しかけると、朝・夜のルーティンを組み立てて返します。

おすすめを増やす美容 AI ではなく、**迷いと無駄買いを減らす美容 AI** です。
購入が必要な場合だけ候補の比較・総額・販売者・選ばなかった理由を提示し、
**利用者が承認したときにだけ**販売サイトへ引き継ぎます。
**「買わない」「手持ちだけで足りる」を、失敗ではなく正式な成功結果として扱う**
エージェンティックコマース AI です。

---

## 1. 解くこと

口コミ・ランキング・診断で商品情報はいくらでも得られますが、利用者は次を判断できません。
「持っている商品をどの順で使うか」「朝夜でどう分けるか」「役割が重複しているのはどれか」
「本当に買う必要があるか」「予算内で 1 つだけなら何か」「忙しい日に省けるのは何か」。

CHIGIRI は「商品検索」ではなく「**意思決定とルーティン編成**」を支援します。

| | 一般的な美容アプリ | CHIGIRI Beauty |
|---|---|---|
| 起点 | 商品カタログ・ランキング | ユーザーの手持ち商品 |
| 目的関数 | 推薦のクリック・購入 | 追加購入額と役割重複の**最小化** |
| 判断基準 | 人気順・口コミ数 | ユーザー固有の制約（予算・時間・除外条件） |
| 説明 | 推薦理由 | 推薦理由 **＋ 不採用理由** |
| 出力 | 商品リスト | 使用順つきの朝・夜ルーティン |

## 2. 設計上いちばん大事な一点

**商品の選定を LLM に任せていません。**

```
入力検証 → ハードフィルタ → 役割分類 → 決定論的スコアリング → 重複検出
  → 工程数の時間調整 → 不足検出 → 買い足し1点の決定
  → 【ここまで LLM 不使用】
  → 決定済みの数点だけを LLM へ渡す → 説明文を生成 → スキーマ検証 → 不正なら決定論的説明へ
```

これにより次が構造的に保証されます。

- **カタログ外の商品が推薦されない** — LLM には許可 ID のリストしか渡さず、返却 ID を照合して
  不一致なら出力ごと破棄する
- **同じ入力から同じ結果が出る** — スコアは純関数、同点時は「安い順 → ID 昇順」で一意に確定
- **AI が落ちてもプロダクトが動く** — `ORCAROUTER_API_KEY` 未設定でも全機能がデモ可能。
  説明文が決定論的なものに変わるだけで、ルーティンの中身と根拠は変わらない
- **除外条件が必ず守られる** — アレルギー・避けたい成分は減点ではなくハードフィルタ

パイプライン図と検証段の詳細は [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md)。

## 3. データを外に出さない構成

「学習に使いません」と書くだけにせず、**外へ出る経路そのものを塞いだうえで**表示しています。

外部 AI への送信は、次の **3 つすべて**が揃ったときにだけ発生します。1 つでも欠ければ送信は起こらず、
それでもルーティンの組み立て・重複検出・買い足し判断はすべて動きます（決定論的な計算のため）。

| 条件 | 初期値 | 誰が決めるか |
|---|---|---|
| `CHIGIRI_EXTERNAL_AI` が `off` でない | on | 運用者（環境変数） |
| **画面での明示的な選択** | **未選択＝送らない** | 利用者 |
| `ORCAROUTER_API_KEY` の設定 | 未設定 | 運用者 |

利用者には最初に一度だけ「AI に文章を任せる／端末内だけで使う」を選んでもらいます。
**選ぶまでは送信しません。** どちらを選んでも結論は変わらず、変わるのは説明文の書き方だけです。

### 型で縛る

判定を通らずに外部送信するコードを**書けなくして**います。

```ts
// server/orcarouter.ts — 外部APIを呼ぶ唯一の関数
export type CallOptions = { /* ... */ grant: ExternalAiGrant };  // ← 必須

// server/ai-policy.ts — 許可証はここでしか作れない
declare const grantBrand: unique symbol;
export type ExternalAiGrant = { readonly [grantBrand]: "external-ai"; /* ... */ };
```

`ExternalAiGrant` はユニークシンボルで印を付けた型のため外部からは値を作れず、
`decideExternalAi()` が許可を出したときにだけ発行されます。`callOrcaRouter` は実行時にも
運用側のキルスイッチを再確認するため、環境変数を切り替えた直後に発行済みの許可証で
送信されることもありません。

### 送るときも最小限にする

許可した場合でも、**アレルギー・避けたい成分の具体名は送りません。** 件数だけを渡し、
除外の判定はサーバー内で完結させます（`避けたい成分: "2件の指定あり（内容は送信していません）"`）。
除外理由の文は決定論的に組み立てたもの（成分名入り）を使うため、表示の具体性は落ちません。

### 保存しない

相談ログ・手持ち商品・買った／見送った記録・アレルギー・肌傾向・入力本文は**すべて端末のみ**。
サーバーは DB に保存せず、記録に残すのは応答時間・成否・選択モデルといった動作指標だけで
**入力本文を含めません**。保存していないため、学習に回せるデータそのものが存在しません。
クレジットカード情報・顔写真は受け取りません。ブラウザ側も CSP の `connect-src 'self'` で
第三者への直接送信を塞いでいます。

`tests/ai-policy.test.ts` は文言ではなく**実際に `fetch` が呼ばれないこと**を確認しています
（未選択時 / 運用側 off / キー無し のいずれも 0 回、説明用プロンプトに成分の具体名を含まない）。

利用者向けの説明と設定は `/privacy`。外部 AI をオンにした場合、その先の事業者がデータを
どう扱うかは保証できません。**保証できないからこそ初期設定を「送らない」にしている**ことも
そのまま画面に書いています。

## 4. LLM のコスト管理

| 手段 | 効果 |
|---|---|
| **呼ばない** | 商品選定・除外・順位づけ・買い足し判定はすべて決定論的。LLM は説明文だけ |
| **二度課金しない** | 同じ問い合わせは応答をキャッシュ（30 分・最大 200 件。鍵はプロンプトの SHA-256） |
| **上限で止める** | 1 日の推定費用が上限に達したら外部呼び出しを停止し決定論的応答へ切り替え |

キャッシュが効くのは**商品選定が決定論的だから**です。同じ条件からは必ず同じプロンプトが生成されます。
上限超過の判定はプライバシー判定と**同じ関門**（`ai-policy.ts`）に載せています。外部へ出る経路が
1 つしかないため、費用の歯止めも 1 か所で効きます。

`model="auto"` で実モデルが決まるため確定価格は分かりません。モデル名から単価表を引き、
不明ならティア既定値を使い、**表示には必ず「推定」と明記**します。

> この回の推定費用 約0.412円（実モデルの単価表からの推定値）
> キャッシュ命中 — 同じ条件の応答を再利用したため、この回の追加費用はありません。

`GET /api/ops` で当日の使用額・残額・キャッシュ命中率・中央応答時間・コマース KPI を返します
（個人に紐づく値は含めません）。

## 5. 重複購入防止 API（B2B）

```
POST /api/b2b/duplicate-check
{ "cart": [{"productId": "lo-hadalabo-shirojyun"}],
  "owned": ["lo-hadalabo-gokujyun"], "unopenedCategories": ["serum"] }

→ { "items": [{ "verdict": "duplicate_role", "message": "化粧水はすでに同じ役割の商品を…" }],
    "summary": { "flaggedCount": 2, "avoidableYen": 2398, "recommendation": "…" },
    "deterministic": true }
```

一般的なレコメンド API が「もっと買わせる」ために使われるのに対し、これは逆に
**「その買い物は要りますか」**を返します。EC 側の価値は返品率と「買ったのに使われない在庫」の削減。

**LLM を呼びません**（応答が安定し費用がかからない）。個人情報も受け取りません（商品 ID のみ）。
何も保存しません。アフィリエイト報酬データは推薦スコアから完全に分離しており、順位計算に入れていません。

## 6. エージェンティックコマース層

一般的なコマースエージェントが「適した商品を見つけて購入完了へ導く」のに対し、CHIGIRI はその前に
**「そもそも新しく購入する必要があるか」**を評価し、`NO_PURCHASE_NEEDED` を**正式な成功状態**として持ちます。

```
INTENT_CAPTURED → INVENTORY_CONFIRMED → ROUTINE_GENERATED → NEED_ASSESSED
   ├→ NO_PURCHASE_NEEDED                      （成功の終端。買わずに完了）
   └→ CANDIDATES_COMPARED → AWAITING_USER_APPROVAL
          ├→ PURCHASE_HANDOFF_READY           （ユーザーの明示操作が必須）
          └→ DECLINED                          （成功の終端。買わない判断）
```

`AWAITING_USER_APPROVAL → PURCHASE_HANDOFF_READY` の遷移だけは、コメントではなく
**型と関数シグネチャ**で制約しています（`transition()` が `userInitiated` を要求し、省略時は
`user_action_required` で失敗）。不正な遷移は例外にせず `false` を返すため、
「進んだことにして処理を続ける」経路が作れません。

### 外部サイトへ移動する唯一の出口

| 段階 | 検証内容 |
|---|---|
| ① 候補提示 | ハードフィルタ・予算・手持ち重複を通過した商品のみ。提携報酬は順位に**一切**含めない |
| ② 承認直前の再検証 | 価格・在庫・予算・除外条件・遷移先 URL を**もう一度**評価（`validateOffer`） |
| ③ トークン発行 | 遷移先 URL を含めて HMAC-SHA256 署名。有効期限 10 分・**単回使用** |
| ④ 遷移時 | 署名・期限・未使用を検証し、**許可リストへ再度かけてから** 303 リダイレクト |

**外部 URL がクライアントへ渡るのは承認成立後だけです。** 承認前の画面が持つのは内部パス
（`/api/commerce/handoff/<token>`）のみで、クエリ文字列から遷移先を受け取る経路は存在しません
（オープンリダイレクト不成立）。`next start` に対する実測:

```
正規リンク（1回目）           → 303  Location: https://www.kao.co.jp/biore/
同じリンクの再利用（2回目）   → 400  「この承認リンクはすでに使用されています」
署名を差し替えたトークン      → 400
本文を書き換えて外部URLを注入 → 400  （署名不一致で遷移せず）
未確認項目を了解せずに承認    → 409  handoff=null, state=AWAITING_USER_APPROVAL
表示価格を偽装して承認        → 409  blockers=["price_changed"]
予算を下回るプロファイル      → 409  blockers=["over_budget"]
```

### 推測しない

「在庫、価格、送料、配送日を推測しない」を、**それらしい数字で埋めない**という形で実装しています。

- 在庫 API を持たないので `availability` は常に `"unknown"`。`"in_stock"` と書かない
- 送料が未確認の販売者では `shippingFee: null` とし、`totalYen` も **`null` のまま**にする
  （送料未確認を 0 円に丸めると、承認画面の「合計額」が嘘になる）
- 承認画面は該当項目に「未確認」バッジを出し、**未確認項目がある場合はチェックボックスでの
  了解なしに承認ボタンが押せません**

### 反実仮想と「買わなかった記録」

「いまの結論が、どの条件で変わるのか」を決定論的に計算して提示します。候補になり得る価格を
境界として列挙し、**その予算で選定を実際にやり直して**結果が変わる点を探します（単なる価格比較ではない）。
候補が 0 件のときは「いくらまで上げれば最初の候補が出るか」を答えます。

> 予算を715円に下げると、提案はニベアサン プロテクト ウォータージェル（715円）に変わります。

買った／見送った／続いたの記録は**利用者の端末のみ**（`localStorage`）。**明示同意を得るまで
一切書き込まず**、同意を取り消すと既存の記録も消えます。記録するのは「どの役割の商品を、
買ったか／見送ったか／続いたか」だけで、肌の悩み・アレルギー・手持ち一覧は含めません。
「続かなかった」商品は、次に候補へ出たとき注意として表示されます。

### 環境変数

| 変数 | 必須 | 説明 |
|---|---|---|
| `CHIGIRI_EXTERNAL_AI` | 任意 | 既定は有効。`off` で外部送信を完全停止（利用者が選ぶまでは既定でも送信しない） |
| `CHIGIRI_LLM_DAILY_BUDGET_JPY` | 任意 | 1 日の AI 利用費の上限（既定 300 円）。超えたら決定論的応答へ |
| `CHIGIRI_LLM_INPUT_JPY_PER_1K` / `_OUTPUT_JPY_PER_1K` | 任意 | 単価を実請求に合わせる場合に指定（未指定はモデル名からの推定） |
| `CHIGIRI_OPS` | 任意 | `1` で開発者向け画面 `/ops` を有効化（未設定時は 404） |
| `ORCAROUTER_API_KEY` | 任意 | 未設定なら決定論的フォールバックのみで動作 |
| `ORCAROUTER_BASE_URL` | 任意 | 既定 `https://api.orcarouter.com/v1` |
| `ORCAROUTER_MODEL_CHEAP` / `_QUALITY` | 任意 | 既定 `auto`（入力の構造化用 / ルーティン説明用） |
| `ORCAROUTER_TIMEOUT_MS` | 任意 | 既定 `20000` |
| `CHIGIRI_HANDOFF_SECRET` | **本番で必須** | 引き継ぎトークンの署名鍵（32 文字以上）。`openssl rand -hex 32` |
| `RAKUTEN_APP_ID` ほか | 任意 | 商品写真の取得。[`docs/OPERATIONS.md`](docs/OPERATIONS.md) 参照 |

API キーは**サーバー側でのみ**読み込みます（`NEXT_PUBLIC_` 接頭辞は使いません）。`server/` 配下は
`server-only` でインポートを封じており、クライアントバンドルへの混入をビルド時に検出します。

`CHIGIRI_HANDOFF_SECRET` は開発時に未設定だと**起動ごとに変わる一時鍵**を自動生成します
（再起動で承認済みリンクが失効するだけ）。`NODE_ENV=production` で未設定の場合は**起動時に失敗**します。
黙って一時鍵で動かすと、複数インスタンス構成で署名検証が通らず「承認したのに遷移できない」が
再現性なく起きるためです。

## 9. OrcaRouter の使い方

OpenAI 互換 API として Route Handler から呼び出し、タスクごとにティアを分けます。

| タスク | ティア | 出力 |
|---|---|---|
| 自然文 → 条件の構造化 | コスト優先 | JSON |
| 確定ルーティンの説明 | 品質優先 | JSON |
| 疎通確認 | コスト優先 | JSON |

`model="auto"` でルーターに選択を委ね、実際に選ばれたモデルをレスポンスヘッダーまたはボディから
取得して**結果画面に表示**します。

**ティア降格**：品質優先ティアが落ちている場合、コスト優先ティアへ降格して 1 度だけ再試行します。

| 失敗の種類 | 挙動 |
|---|---|
| 5xx / 429 / タイムアウト / ネットワーク | 下位ティアで再試行 |
| 4xx（認証・リクエスト誤り） | 再試行しない（同じ結果を繰り返し課金しないため） |
| 両方失敗 | 決定論的な説明へ切り替え。ルーティンの中身は変わらない |

`tests/orcarouter-integration.test.ts` は OpenAI 互換の応答を返すサーバーを実際に立てて
**本物のクライアントを HTTP で通します**（送信形式・認証ヘッダ・選択モデル取得・費用推定・
キャッシュ・5xx/4xx/空応答・タイムアウト・ティア降格を検証）。

実測で確認していること — 許可あり: `ai.used=true` で要約と採用理由が AI の文章に変わる。
2 回目: `cached=true` で費用 0。許可なし: `ai.used=false reason=user_local_only` で決定論的な文章。
**どの場合も朝のルーティンの商品 ID は完全に一致**します。

## 10. 安全設計（薬機法・医療境界）

CHIGIRI は美容上の意思決定支援であり、医療サービスではありません。

- **受診勧奨ゲート**：痛み・腫れ・出血・化膿・水疱・急激な悪化などが入力された場合、
  推薦を**実行せず**医療機関への相談を促します（減点ではなく停止）
- **医療相談の切り分け**：疾患名・治療・処方に関する相談も推薦を停止します
- **許可表現のホワイトリスト**：説明文は `data/allowed-claims.json`（化粧品の効能の範囲）から生成。
  医薬部外品の表現は `isQuasiDrug: true` の商品にのみ許可し、違反はカタログ読み込み時に例外化
- **禁止表現の検出**：AI 出力に「治る」「改善します」「絶対安全」等が含まれたら、その出力を破棄して
  決定論的説明へ切り替え
- **不確実性の明示**：成分表示だけからは濃度・処方・使用量が不明であることを常に併記

全画面に「医療上の診断や治療を提供するものではありません。肌に異常がある場合は使用を中止し、
医師や専門家へ相談してください」を表示します。

### セキュリティ

| 対策 | 実装 |
|---|---|
| オープンリダイレクト | 遷移先はサーバー側カタログ由来のみ。許可リスト＋HTTPS 必須＋ポート/認証情報/制御文字を拒否（`url-allowlist.ts`） |
| 承認の偽装 | HMAC-SHA256 署名・10 分の有効期限・単回使用（`handoff-token.ts`） |
| ホスト偽装 | 完全一致とドット境界のサブドメインのみ。`endsWith` を使わないため `evil-www.kao.co.jp` は通らない |
| セキュリティヘッダー | CSP（`default-src 'self'` / `connect-src 'self'` / `frame-ancestors 'none'`）、HSTS、`nosniff`、`Permissions-Policy` |
| クリックジャッキング | `frame-ancestors 'none'` ＋ `X-Frame-Options: DENY`（承認ボタンを踏ませない） |
| プロンプト注入 | 役割偽装表記・チャットテンプレートトークン・区切り記号を入口で除去し、データとして囲む（`prompt-safety.ts`） |
| 費用・可用性 | API ごとのレート制限＋本文サイズ上限（`api-guard.ts`） |
| 情報の露出 | Zod の `issues` を返さない。エラー本文に内部構造を含めない |
| ログの秘匿 | 監査ログは「何が起きたか」のみ。IP・肌の悩み・アレルギー・手持ち一覧・入力本文を保存しない |
| 決済情報 | 決済を行わず、カード情報を受け取らない・保存しない・LLM へ送らない |

**プロンプト注入が成功しても商品選定は変わりません。** 除外・順位づけ・買い足し判定はすべて
決定論的なコードが行い、LLM 出力は Zod と許可 ID リストで検証してから使うためです。
注入対策は「説明文の乗っ取り」と「構造化出力を壊しての可用性低下」に対する二次防御です。

## 12. 推薦スコア

```
score = 美容上の関心との一致 × 0.30 + 肌傾向との一致 × 0.20 + 手持ち活用への貢献 × 0.20
      + 予算適合 × 0.15 + 使用感との一致 × 0.10 + 入手しやすさ × 0.05 − 注意要素ペナルティ
```

- **関心は優先順位付き**で、先頭ほど重み `1/(i+1)` が大きい。**手持ち商品は予算適合が常に満点**
  （追加費用が発生しないため）
- 役割重複ペナルティと工程過多ペナルティは、カテゴリー内順位と使用可能時間が確定する
  `routine-builder` 側で適用する
- **工程の時間調整**：`critical / recommended / optional` を設定し、使用可能時間を超える場合は
  `optional → recommended` の順、同じ重要度ではスコアの低いものから外す。`critical` は外さない
- **使用タイミングを考慮した重複解決**：役割が重複していても使用タイミングが違えば両方活用する
  （夜専用クリームと朝夜兼用乳液を持つなら、夜はクリーム・朝は乳液）

**ルーティンは 3 案**（標準・時短・じっくり）。いずれも同じ決定論的ロジックで、
使える時間の前提だけを変えて組み立てるため、案ごとに基準がぶれません。
**中身が同じになった案は出しません。** あわせて手持ちから成立する組み立て方の総数を数えて
表示します（「手持ちからは 48通り の組み立て方があります」）。概算ではなく実際に成立する並びの数で、
数え方の定義も画面に書いています。

## 13. 商品データの制約（重要）

`data/products.json` は日本で購入できるコスメ **92 点**の手動整備カタログです
（スキンケア 46 / メイク 15 / ヘア 12 / ネイル 10 / ボディ 9）。

**現状、全商品が `sourceCheckedAt: null` / `dataConfidence: "seed"` です。**
公式ブランドサイトとの逐一の突合が未完了であることを意味します。価格は編集時点の参考価格で
実売価格を保証せず、`officialUrl` も商品ページ単位の検証は未実施です。UI では該当商品に
「公式突合 未完了（参考データ）」バッジを表示し、根拠が確認済みであるかのようには表示しません。

**商品写真も 92 点すべて未登録**で、役割とブランドから決まる線画を表示しています
（詳細画面に「写真未登録」と明記）。

**本番運用の前に、全 92 点を公式ページと突合する必要があります。**
手順は [`docs/OPERATIONS.md`](docs/OPERATIONS.md)。突合は人が公式ページを開いて確認する作業で、
自動では行いません（確認していないものを確認したことにしてしまう危険があるため）。

## 14. 保証していること

| 受け入れ条件 | 担保方法 |
|---|---|
| カタログ外の商品を AI が推薦しない | 許可 ID リスト照合＋不一致で出力破棄（`explanation.ts`） |
| 明示的な除外条件に違反しない | ハードフィルタ＋テスト S13/S14 |
| 同じ入力から同じ結果になる | 純関数スコア＋一意なタイブレーク（テスト S26） |
| AI が失敗してもルーティンを表示できる | 決定論パイプラインが独立（`skipLlm` / キー未設定で検証） |
| 公式 URL のない商品を根拠ありとしない | `sourceCheckedAt: null` を未検証として表示 |
| 全 API 入力・AI 出力を Zod で検証 | 入力・出力・LLM 応答すべて |
| API キーがクライアントバンドルに含まれない | `server-only` ＋ ビルド成果物の走査で確認 |
| 手持ちだけで足りる場合に購入を提案しない | `NO_PURCHASE_NEEDED` を成功終端として実装 |
| 最大買い足し数・予算を超えない | 候補生成時と承認直前の二重チェック（`over_budget`） |
| 採用・不採用の両方の理由を表示 | 全候補に `notChosenReason` を必須化（テストで検証） |
| 承認なしで外部遷移・注文処理をしない | 状態機械が `userInitiated` を要求＋署名付きトークン |
| 外部 URL を許可リストで検証 | 発行時と遷移時の二重検証（`url-allowlist.ts`） |
| 既定設定で外部へ送信しない | `fetch` が呼ばれないことをテストで検証（`ai-policy.test.ts`） |
| スマホ幅で横スクロールが発生しない | `overflow-x: hidden` ＋ モバイルファースト設計 |

## 15. デモ

`/demo` に入力不要の 4 シナリオがあります。用意しているのは**入力（条件と手持ち）だけ**で、
結果は通常とまったく同じ経路から出します。デモ専用の分岐や、あらかじめ書いた結論は持ちません。

| シナリオ | 見えるもの |
|---|---|
| 1 点だけ足りない人 | 買い足しは 1 点だけ。候補比較と承認フローへ |
| 買わなくていい人 | 「買い足しは必要ありません」— このサービスの中心的な結果 |
| 重複買いしていた人 | 役割の重複と、今回使わない理由 |
| 予算が足りない人 | 条件に合う商品がないことを説明し、購入を勧めない |

`tests/demo-scenarios.test.ts` が各シナリオの結果を検証します。カタログの `usageTiming` 一つで
「買い足し不要」が「1 点提案」に変わるため、説明文と実際の結果がずれたら検知できます。

**手動デモの流れ（3 分）**：`/chat` で条件を入力 → 手持ち 6 点を選択（日焼け止めなし）→
組み立て → *手持ち 5 点を活用、必要なのは日焼け止め 1 点だけ、約 6,644 円の購入を回避* →
標準／時短／じっくりの切り替えと「48 通り」の開示 → 重複と不採用理由 →
予算を 1000 円へ変更して再計算 → 候補 3 件の比較 → 「予算を 715 円に下げると提案が変わります」→
承認画面（未確認項目を了解するまで承認できない）→「今回は買わない」を承認と同じ大きさで提示 →
承認した場合のみ署名付き・10 分・単回使用のリンクで 303 遷移。

## 16. 実装していないもの・本番化の前に必要なこと

顔写真による肌診断／医療的な診断／治療方法の提案／自動スクレイピング／1000 件以上の商品 DB／
**アプリ内決済・自律購入・カード情報の保存**／本格的な認証／SNS・コミュニティ／ネイティブアプリ／
ベクトル DB／ファインチューニング／リアルタイム在庫・価格取得／プッシュ通知／アフィリエイト優先表示

| 項目 | 現状 | 必要な対応 |
|---|---|---|
| 在庫・価格・送料 | すべて未確認として表示 | 販売者 API または ACP/UCP 接続で実データを取得 |
| 商品カタログ | 92 点・`sourceCheckedAt: null` | [`docs/OPERATIONS.md`](docs/OPERATIONS.md) の突合手順 |
| レート制限 | プロセス内メモリ | 複数インスタンスでは Redis 等の共有ストアへ |
| 使用済みトークン | プロセス内メモリ | 同上（現状は再起動で使用済み記録が消える） |
| 監査ログ | 標準出力＋直近 200 件 | 永続化と保持期間ポリシーの設定 |
| 美容グラフ | 端末内のみ | サーバー同期する場合は同意管理・削除権の実装が別途必要 |

`CommerceAdapter` インターフェースを挟んであるため、実 EC 接続や ACP / UCP への差し替えは
`static-adapter.ts` の置き換えで済みます。UI・状態機械・承認フローは変更不要です。
