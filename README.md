# CHIGIRI Beauty

> 買う前に、今あるものをつなぐ。

CHIGIRI Beauty は、手持ちの化粧品を再編成し、本当に不足している商品だけを理由付きで提案する
**美容ルーティン最適化AI** です。チャットで話しかけると、朝・夜のルーティンを組み立てて返します。

おすすめを増やす美容AIではなく、**迷いと無駄買いを減らす美容AI**です。

---

## 1. このプロダクトが解くこと

ユーザーは口コミ・ランキング・診断から商品情報をいくらでも得られますが、次の判断ができません。

- 持っている商品をどの順番で使えばよいか
- 朝と夜でどう分ければよいか
- 役割が重複している商品はどれか
- 本当に新しい商品を買う必要があるか
- 予算内で1つだけ買うなら何か
- 忙しい日には何を省略できるか

CHIGIRI は「商品検索」ではなく「**意思決定とルーティン編成**」を支援します。

### 競合との違い

| | 一般的な美容アプリ | CHIGIRI Beauty |
|---|---|---|
| 起点 | 商品カタログ・ランキング | ユーザーの手持ち商品 |
| 目的関数 | 推薦のクリック・購入 | 追加購入額と役割重複の**最小化** |
| 判断基準 | 人気順・口コミ数 | ユーザー固有の制約（予算・時間・除外条件） |
| 説明 | 推薦理由 | 推薦理由 **＋ 不採用理由** |
| 出力 | 商品リスト | 使用順つきの朝・夜ルーティン |

## 2. 設計上いちばん大事な一点

**商品の選定を LLM に任せていません。**

```
入力検証 → ハードフィルタ → 役割分類 → 決定論的スコアリング → 重複検出
  → 工程数の時間調整 → 不足検出 → 買い足し1点の決定
  → 【ここまで LLM 不使用】
  → 決定済みの数点だけを LLM へ渡す → 説明文を生成 → スキーマ検証 → 不正なら決定論的説明へ
```

この設計により、次が構造的に保証されます。

- **カタログ外の商品が推薦されない** — LLM には許可 ID のリストしか渡さず、返却 ID を照合して不一致なら出力ごと破棄する
- **同じ入力から同じ結果が出る** — スコアは純関数、同点時は「安い順 → ID 昇順」で一意に確定
- **AI が落ちてもプロダクトが動く** — `ORCAROUTER_API_KEY` 未設定でも全機能がデモ可能。説明文が決定論的なものに変わるだけで、ルーティンの中身と根拠は変わらない
- **除外条件が必ず守られる** — アレルギー・避けたい成分は減点ではなくハードフィルタ

### 環境変数

| 変数 | 必須 | 説明 |
|---|---|---|
| `ORCAROUTER_API_KEY` | 任意 | 未設定なら決定論的フォールバックのみで動作 |
| `ORCAROUTER_BASE_URL` | 任意 | 既定 `https://api.orcarouter.com/v1` |
| `ORCAROUTER_MODEL_CHEAP` | 任意 | 既定 `auto`（入力の構造化用） |
| `ORCAROUTER_MODEL_QUALITY` | 任意 | 既定 `auto`（ルーティン説明用） |
| `ORCAROUTER_TIMEOUT_MS` | 任意 | 既定 `20000` |

APIキーは**サーバー側でのみ**読み込みます（`NEXT_PUBLIC_` 接頭辞は使いません）。
`server/` 配下は `server-only` でインポートを封じており、クライアントバンドルへの混入をビルド時に検出します。

## 4. デプロイ（Vercel）

GitHub連携で入れるのが最短です。push するたびに自動デプロイされます。

1. https://vercel.com/new を開く
2. `keyakizakap-alt/beauty-apps-chigiri` を **Import**
3. 設定はすべて自動検出のままでよい（Framework: Next.js / Build: `next build`）
4. **Environment Variables** — 未設定でもデプロイは成功し、全機能がデモできます。
   OrcaRouter を有効にする場合のみ次を追加してください。

   | Name | Value |
   |---|---|
   | `ORCAROUTER_API_KEY` | 発行されたキー |
   | `ORCAROUTER_BASE_URL` | `https://api.orcarouter.com/v1` |

   `NEXT_PUBLIC_` を付けないでください。付けるとクライアントバンドルへ露出します。
5. **Deploy**

MVP ブランチを確認したい場合は、Import 後に Production Branch を
`claude/chigiri-beauty-mvp-cn3wlv` に変更するか、そのブランチへの push で作られる
Preview URL を使ってください。

DB を使わないため、ほかに必要な設定はありません
（プロファイルはブラウザの localStorage にのみ保存されます）。

## 5. OrcaRouter の使い方

OpenAI 互換 API として Route Handler から呼び出します。

| タスク | ティア | モデル | 出力 |
|---|---|---|---|
| 自然文 → 条件の構造化 | コスト優先 | `auto` | JSON |
| 確定ルーティンの説明 | 品質優先 | `auto` | JSON |

`model="auto"` でルーターに選択を委ね、実際に選ばれたモデルを
レスポンスヘッダー（`x-orcarouter-model` 等）またはボディの `model` から取得し、
**結果画面に表示**します。

ログに保存するもの／しないもの:

- 保存する: リクエストID・タスク種別・選択モデル・応答時間・成否・JSON検証結果・フォールバック有無・推定トークン数
- 保存しない: 氏名・顔写真・詳細な健康情報・APIキー・**入力本文**

## 6. 安全設計（薬機法・医療境界）

CHIGIRI は美容上の意思決定支援であり、医療サービスではありません。

- **受診勧奨ゲート**: 痛み・腫れ・出血・化膿・水疱・急激な悪化などが入力された場合、
  推薦を**実行せず**医療機関への相談を促します（減点ではなく停止）
- **医療相談の切り分け**: 疾患名・治療・処方に関する相談も推薦を停止します
- **許可表現のホワイトリスト**: 説明文は `data/allowed-claims.json`（化粧品の効能の範囲）から生成。
  医薬部外品の表現は `isQuasiDrug: true` の商品にのみ許可し、違反はカタログ読み込み時に例外化
- **禁止表現の検出**: AI 出力に「治る」「改善します」「絶対安全」「副作用がない」等が含まれた場合、
  その出力を破棄して決定論的説明へ切り替え
- **不確実性の明示**: 成分表示だけからは濃度・処方・使用量が不明であることを常に併記

全画面に次を表示します。

> 本サービスは美容情報の整理を目的としたもので、医療上の診断や治療を提供するものではありません。
> 肌に異常がある場合は使用を中止し、医師や専門家へ相談してください。

## 8. 推薦スコア

```
score =
    美容上の関心との一致 × 0.30
  + 肌傾向との一致       × 0.20
  + 手持ち活用への貢献   × 0.20
  + 予算適合             × 0.15
  + 使用感との一致       × 0.10
  + 入手しやすさ         × 0.05
  - 注意要素ペナルティ
```

役割重複ペナルティと工程過多ペナルティは、カテゴリー内順位と使用可能時間が確定する
`routine-builder` 側で適用します。

**関心は優先順位付き**で、先頭ほど重み `1/(i+1)` が大きくなります。
**手持ち商品は予算適合が常に満点**です（追加費用が発生しないため）。

### 工程の時間調整

朝夜それぞれの必要カテゴリーに `critical / recommended / optional` を設定し、
使用可能時間を超える場合は `optional → recommended` の順、
同じ重要度の中ではスコアの低いものから外します。`critical` は外しません。

### 使用タイミングを考慮した重複解決

役割が重複していても、使用タイミングが違えば両方を活用します。
夜専用クリームと朝夜兼用乳液を持っている場合、夜はクリーム・朝は乳液を使い、
「重複しているから片方を捨てる」という結論にはしません。

## 9. 商品データについて（重要な制約）

`data/products.json` は日本で購入できる日本・韓国コスメ **46点**（洗顔・化粧水・美容液・乳液クリーム・日焼け止め）の手動整備カタログです。

**現状、全商品が `sourceCheckedAt: null` / `dataConfidence: "seed"` です。**
これは「公式ブランドサイトとの逐一の突合が未完了」であることを意味します。

- 価格は編集時点の**参考価格**であり、実売価格を保証しません
- `officialUrl` はブランド公式サイトを指しますが、商品ページ単位の検証は未実施です
- UI では該当商品に「公式突合 未完了（参考データ）」バッジを表示し、
  根拠が確認済みであるかのようには表示しません

**本番運用の前に、全46点を公式ページと突合し `sourceCheckedAt` を埋める必要があります。**
突合済みの商品は `dataConfidence: "official"` に変更してください。

## 10. 品質基準の達成状況

| 受け入れ条件 | 状態 | 担保方法 |
|---|---|---|
| カタログ外の商品をAIが推薦しない | ✅ | 許可IDリスト照合＋不一致で出力破棄（`explanation.ts`） |
| 明示的な除外条件に違反しない | ✅ | ハードフィルタ＋テスト S13/S14 |
| 同じ入力から同じ結果になる | ✅ | 純関数スコア＋一意なタイブレーク（テスト S26） |
| AIが失敗してもルーティンを表示できる | ✅ | 決定論パイプラインが独立（`skipLlm` / キー未設定で検証） |
| 公式URLのない商品を根拠ありとしない | ✅ | `sourceCheckedAt: null` を未検証として表示 |
| 全API入力・AI出力をZodで検証 | ✅ | 入力・出力・LLM応答すべて |
| APIキーがクライアントバンドルに含まれない | ✅ | `server-only` ＋ ビルド成果物の走査で確認 |
| スマホ幅で横スクロールが発生しない | ✅ | `overflow-x: hidden` ＋ モバイルファースト設計 |
| 20件以上のテストシナリオ | ✅ | 89ケース（うちシナリオ S01〜S34） |

## 11. デモの流れ（3分）

1. `/chat` で「混合肌で毛穴と乾燥が気になります。予算は3000円くらい」と入力
2. 「手持ち」から6点を選択（洗顔1・化粧水2・美容液1・乳液2、**日焼け止めなし**）
3. 「この条件で組み立てる」
4. → **手持ち6商品のうち5商品を活用。新しく必要なのは日焼け止め1点だけ。約6,644円の購入を回避**
5. 朝・夜ルーティンがタイムラインで表示される
6. 化粧水の役割が重複していることと、その1点を今回使わない理由が表示される
7. 買い足し候補1点＋次点候補＋公式リンク
8. 「なぜこれを選んだか」を開くと採用理由、根拠パネルに公式URLと OrcaRouter の選択モデル
9. 予算を1000円に変更 → 再計算で提案商品が変わる
10. 「おすすめを増やす美容AIではなく、迷いと無駄買いを減らす美容AI」
