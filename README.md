# CHIGIRI Beauty

> 買う前に、今あるものをつなぐ。

CHIGIRI Beauty は、手持ちの化粧品を再編成し、本当に不足している商品だけを理由付きで提案する
**美容ルーティン最適化AI** です。チャットで話しかけると、朝・夜のルーティンを組み立てて返します。

おすすめを増やす美容AIではなく、**迷いと無駄買いを減らす美容AI**です。

そのうえで、購入が必要な場合だけ、候補の比較・総額・販売者・選ばなかった理由を提示し、
**あなたが承認したときにだけ**販売サイトへ引き継ぎます。
**「買わない」「手持ちだけで足りる」を、失敗ではなく正式な成功結果として扱う**
エージェンティックコマースAIです。

---

## 1. このプロダクトが解くこと

ユーザーは口コミ・ランキング・診断から商品情報をいくらでも得られますが、次の判断ができません。

- 持っている商品をどの順番で使えばよいか
- 朝と夜でどう分ければよいか
- 役割が重複している商品はどれか
- 本当に新しい商品を買う必要があるか
- 予算内で1つだけ買うなら何か
- 忙しい日には何を省略できるか

CHIGIRI は「商品検索」ではなく「**意思決定とルーティン編成**」を支援します。

### 競合との違い

| | 一般的な美容アプリ | CHIGIRI Beauty |
|---|---|---|
| 起点 | 商品カタログ・ランキング | ユーザーの手持ち商品 |
| 目的関数 | 推薦のクリック・購入 | 追加購入額と役割重複の**最小化** |
| 判断基準 | 人気順・口コミ数 | ユーザー固有の制約（予算・時間・除外条件） |
| 説明 | 推薦理由 | 推薦理由 **＋ 不採用理由** |
| 出力 | 商品リスト | 使用順つきの朝・夜ルーティン |

## 2. 設計上いちばん大事な一点

**商品の選定を LLM に任せていません。**

```
入力検証 → ハードフィルタ → 役割分類 → 決定論的スコアリング → 重複検出
  → 工程数の時間調整 → 不足検出 → 買い足し1点の決定
  → 【ここまで LLM 不使用】
  → 決定済みの数点だけを LLM へ渡す → 説明文を生成 → スキーマ検証 → 不正なら決定論的説明へ
```

この設計により、次が構造的に保証されます。

- **カタログ外の商品が推薦されない** — LLM には許可 ID のリストしか渡さず、返却 ID を照合して不一致なら出力ごと破棄する
- **同じ入力から同じ結果が出る** — スコアは純関数、同点時は「安い順 → ID 昇順」で一意に確定
- **AI が落ちてもプロダクトが動く** — `ORCAROUTER_API_KEY` 未設定でも全機能がデモ可能。説明文が決定論的なものに変わるだけで、ルーティンの中身と根拠は変わらない
- **除外条件が必ず守られる** — アレルギー・避けたい成分は減点ではなくハードフィルタ

## 3. データを外に出さない構成

「学習に使いません」と書くだけにせず、**外へ出る経路そのものを塞いだうえで**表示しています。

### 初期状態で外部へ送信されるもの：なし

外部AIサービスへの送信は、次の**3つすべて**が揃ったときにだけ発生します。
1つでも欠けていれば送信は起こらず、それでもルーティンの組み立て・重複検出・買い足し判断は
すべて動きます（もともとAIではなく決定論的な計算で行っているため）。

| 条件 | 初期値 | 誰が決めるか |
|---|---|---|
| `CHIGIRI_EXTERNAL_AI` が `off` でない | on（OrcaRouter を使う前提） | 運用者（環境変数） |
| **画面での明示的な選択** | **未選択＝送らない** | 利用者 |
| `ORCAROUTER_API_KEY` の設定 | 未設定 | 運用者 |

利用者には最初に一度だけ「AIに文章を任せる／端末内だけで使う」を選んでもらいます。
**選ぶまでは送信しません。** 既定値のまま黙って送ることも、
黙って送らないと決めつけることもしない、という形にしています。
どちらを選んでも結論は変わらず、変わるのは説明文の書き方だけです。

### 型で縛る

判定を通らずに外部送信するコードを**書けなくして**います。

```ts
// server/orcarouter.ts — 外部APIを呼ぶ唯一の関数
export type CallOptions = {
  ...
  grant: ExternalAiGrant;   // ← 必須
};

// server/ai-policy.ts — 許可証はここでしか作れない
declare const grantBrand: unique symbol;
export type ExternalAiGrant = { readonly [grantBrand]: "external-ai"; ... };
```

`ExternalAiGrant` はユニークシンボルで印を付けた型のため、外部からは値を作れません。
`decideExternalAi()` が許可を出したときにだけ発行されます。
さらに `callOrcaRouter` は実行時にも運用側のキルスイッチを再確認するため、
環境変数を切り替えた直後に発行済みの許可証で送信されることもありません。

### 送るときも最小限にする

許可した場合でも、**アレルギー・避けたい成分の具体名は送りません**。
件数だけを渡し、除外の判定はサーバー内で完結させています。
除外された商品の理由文は、決定論的に組み立てたもの（成分名入り）をそのまま採用するため、
表示される説明の具体性は落ちません。

```
避けたい成分: "2件の指定あり（内容は送信していません）"
```

### 保存しない

| データ | 保存先 | 外部AIへの送信 |
|---|---|---|
| 相談ログ（会話の全文） | 端末のみ | 送らない |
| 手持ち商品の一覧 | 端末のみ | 送らない |
| 買った／見送った記録 | 端末のみ（同意後） | 送らない |
| アレルギー・避けたい成分 | 端末のみ | 送らない（件数のみ） |
| 肌傾向・関心・予算・時間 | 端末のみ | 許可時のみ |
| 入力した文章 | 端末のみ | 許可時のみ |
| クレジットカード情報・顔写真 | 受け取らない | 送らない |

サーバーはこれらをデータベースに保存しません。記録に残すのは応答時間・成否・
選択モデルといった動作の指標だけで、**入力本文を含めません**。
保存していないため、学習に回せるデータそのものが存在しません。

ブラウザ側も CSP の `connect-src 'self'` で第三者への直接送信を塞いでいます。

### 検証

`tests/ai-policy.test.ts` は文言ではなく**実際に `fetch` が呼ばれないこと**を確認しています。

```
利用者が未選択                 → fetch 呼び出し 0 回・条件抽出は規則ベースで成立
運用側 off ＋ 利用者が許可      → fetch 呼び出し 0 回
APIキー無し ＋ 利用者が許可     → fetch 呼び出し 0 回
説明用プロンプト                → 「アルコール」「香料」等の具体名を含まない
```

利用者向けの説明と設定は `/privacy` にあります。
外部AIをオンにした場合、その先の事業者がデータをどう扱うかは
このアプリからは保証できません。**保証できないからこそ初期設定を「送らない」にしています**
という点も、そのまま画面に書いています。

## 4. LLM のコスト管理

LLM は「動けばよい」ものではなく、**呼ぶたびに課金される外部依存**として扱っています。

### 3段構えで抑える

| 手段 | 効果 |
|---|---|
| **呼ばない** | 商品選定・除外・順位づけ・買い足し判定はすべて決定論的。LLM は説明文だけ |
| **二度課金しない** | 同じ問い合わせは応答をキャッシュ（30分・最大200件） |
| **上限で止める** | 1日の推定費用が上限に達したら、外部呼び出しを停止して決定論的応答へ切り替え |

キャッシュが効くのは、**商品選定が決定論的だから**です。同じ条件からは必ず同じプロンプトが
生成されるため、再計算やデモの繰り返しではほぼ確実に命中します。
鍵はプロンプトの SHA-256 で、鍵から本文を復元できません。

上限超過の判定は、プライバシーの判定と**同じ関門**（`ai-policy.ts`）に載せています。
外部へ出る経路が1つしかないため、費用の歯止めも1か所で効きます。

```
CHIGIRI_LLM_DAILY_BUDGET_JPY   1日の上限（既定 300円）
CHIGIRI_LLM_INPUT_JPY_PER_1K   単価を実際の請求に合わせる場合に指定
CHIGIRI_LLM_OUTPUT_JPY_PER_1K
```

### 費用を隠さない

`model="auto"` で実モデルが決まるため確定価格は分かりません。
そこでモデル名から単価表を引き、不明ならティア既定値を使い、
**表示には必ず「推定」と明記**します。単価は環境変数で実請求に合わせられます。

結果画面には毎回こう出ます。

> この回の推定費用 約0.412円（実モデルの単価表からの推定値）
> キャッシュ命中 — 同じ条件の応答を再利用したため、この回の追加費用はありません。

`GET /api/ops` で当日の使用額・残額・キャッシュ命中率・中央応答時間・
コマース KPI を返します（個人に紐づく値は含めません）。

## 5. ビジネス面の実装

設計書 §19 の収益モデルのうち、**重複購入防止 API** を実際に動く形にしています。

```
POST /api/b2b/duplicate-check
{ "cart": [{"productId": "lo-hadalabo-shirojyun"}],
  "owned": ["lo-hadalabo-gokujyun"],
  "unopenedCategories": ["serum"] }

→ { "items": [{ "verdict": "duplicate_role",
                "message": "化粧水はすでに同じ役割の商品をお持ちです。…" }],
    "summary": { "flaggedCount": 2, "avoidableYen": 2398,
                 "recommendation": "2点が手持ちと役割で重複しています。見送ると約2,398円の購入を避けられます。" },
    "deterministic": true }
```

一般的なレコメンド API は「もっと買わせる」ために使われます。これはその逆で、
**「その買い物は要りますか」**を返します。EC 側の価値は、返品率と
「買ったのに使われない在庫」を減らせることにあります。

この API は **LLM を呼びません**（応答が安定し、費用がかからない）。
個人情報も受け取りません（商品 ID だけで、肌の悩みや氏名を要求しない）。
何も保存しません。

CHIGIRI 本体が「買わない判断」を売りにしている以上、
アフィリエイト報酬で稼ぐ形は思想と衝突します。
報酬データは推薦スコアから完全に分離しており、順位計算に一切入れていません。

## 6. エージェンティックコマース層

一般的なコマースエージェントは「適した商品を見つけて購入完了へ導く」ことを目的にします。
CHIGIRI はその前に **「そもそも新しく購入する必要があるか」** を評価し、
`NO_PURCHASE_NEEDED` を**正式な成功状態**として持ちます。

### 状態モデル

```
INTENT_CAPTURED → INVENTORY_CONFIRMED → ROUTINE_GENERATED → NEED_ASSESSED
   ├→ NO_PURCHASE_NEEDED                      （成功の終端。買わずに完了）
   └→ CANDIDATES_COMPARED → AWAITING_USER_APPROVAL
          ├→ PURCHASE_HANDOFF_READY           （ユーザーの明示操作が必須）
          └→ DECLINED                          （成功の終端。買わない判断）
```

`AWAITING_USER_APPROVAL → PURCHASE_HANDOFF_READY` の遷移だけは、
コメントではなく**型と関数シグネチャ**で制約しています
（`transition()` が `userInitiated` を要求し、省略時は `user_action_required` で失敗する）。
不正な遷移は例外にせず `false` を返すため、「進んだことにして処理を続ける」経路が作れません。

### 外部サイトへ移動する唯一の出口

購入承認は、次の 4 段階をすべて通った場合にだけ成立します。

| 段階 | 検証内容 |
|---|---|
| ① 候補提示 | ハードフィルタ・予算・手持ち重複を通過した商品のみ。提携報酬は順位に**一切**含めない |
| ② 承認直前の再検証 | 価格・在庫・予算・除外条件・遷移先URLを**もう一度**評価（`validateOffer`） |
| ③ トークン発行 | 遷移先URLを含めて HMAC-SHA256 署名。有効期限10分・**単回使用** |
| ④ 遷移時 | 署名・期限・未使用を検証し、**許可リストへ再度かけてから** 303 リダイレクト |

**外部URLがクライアントへ渡るのは、承認が成立した後だけです。**
承認前の画面が持つのは内部パス（`/api/commerce/handoff/<token>`）のみで、
クエリ文字列から遷移先を受け取る経路は存在しません（オープンリダイレクト不成立）。

実測（`next start` に対する検証）:

```
正規リンク（1回目）          → 303  Location: https://www.kao.co.jp/biore/
同じリンクの再利用（2回目）  → 400  「この承認リンクはすでに使用されています」
署名を差し替えたトークン     → 400
本文を書き換えて外部URLを注入 → 400  （署名不一致で遷移せず）
未確認項目を了解せずに承認   → 409  handoff=null, state=AWAITING_USER_APPROVAL
表示価格を偽装して承認       → 409  blockers=["price_changed"]
予算を下回るプロファイル     → 409  blockers=["over_budget"]
```

### 推測しないことの実装

設計書の「在庫、価格、送料、配送日を推測しない」を、
**それらしい数字で埋めない**という形で実装しています。

- 在庫 API を持たないので `availability` は常に `"unknown"`。`"in_stock"` と書きません
- 送料が未確認の販売者では `shippingFee: null` とし、`totalYen` も **`null` のまま**にします
  （送料未確認を 0 円に丸めると、承認画面の「合計額」が嘘になるため）
- 承認画面は該当項目に「未確認」バッジを出し、
  **未確認項目がある場合はチェックボックスでの了解なしに承認ボタンが押せません**

### 反実仮想：予算の転換点

「いまの結論が、どの条件で変わるのか」を決定論的に計算して提示します。

> 予算を715円に下げると、提案はニベアサン プロテクト ウォータージェル（715円）に変わります。
> 役割は同じで、容量と使用感が変わります。

候補になり得る価格を境界として列挙し、**その予算で選定を実際にやり直して**
結果が変わる点を探します（単なる価格比較ではありません）。
候補が0件のときは「いくらまで上げれば最初の候補が出るか」を答えます。

### 買わなかった記録（パーソナル美容グラフの入口）

- 保存先は**利用者の端末のみ**（`localStorage`）。サーバーへ送信しません
- **明示同意を得るまで一切書き込みません**。同意を取り消すと既存の記録も消えます
- 記録するのは「どの役割の商品を、買ったか／見送ったか／続いたか」だけで、
  肌の悩み・アレルギー・手持ち一覧は含めません
- 「続かなかった」と答えた商品は、次に候補へ出たとき注意として表示されます

```bash
npm install
cp .env.example .env.local   # APIキーは任意（未設定でも動作します）
npm run dev                  # http://localhost:3000
```

```bash
npm test        # Vitest（251ケース）

npm run typecheck

npm run icons   # app/icon.svg から PWA/iOS 用 PNG を再生成

npm run verify:export  # 公式ページ突合のワークシートを書き出す（→ 13章）
```

### アプリアイコンとオープニング

アイコンは **重なり合う2つの輪** で「買う前に、今あるものをつなぐ」を表しています。
重なった部分（レンズ形）に桜色を置き、すでに持っているもの同士がつながる地点を中心に据えました。

- `app/icon.svg` — 原本。ブラウザのタブ用（SVG なのでどの解像度でも滲まない）
- `public/icons/*.png` — `npm run icons` で SVG から書き出したもの。
  ホーム画面追加時の iOS / Android 用。リクエストごとの画像生成を避けるためコミットしています
- `maskable-512.png` は Android のアダプティブアイコン用に角丸を付けず、
  中央80%のセーフゾーンに収まるよう縮めています（OS 側が任意の形に切り抜くため）
- `app/manifest.ts` — ホーム画面から開くとブランド色のスタンドアロン表示になります

アプリを開くと、アイコンとタグラインのオープニングが一度だけ表示されます（`components/AppSplash.tsx`）。

- フェードアウトは **CSS アニメーションだけで完結**します。
  JS が動かない環境でもオーバーレイが居座って操作を塞ぐことがありません
- `sessionStorage` で「同じタブでは1回だけ」。画面遷移やリロードでは再表示しません
- `prefers-reduced-motion` では拡大・移動をやめ、短く消えるだけにします
- 装飾のため `aria-hidden`。読み上げは本文から始まります

### デモ（入力不要）

`/demo` に代表的な4つの状況を用意しています。手持ちを1点ずつ選ばなくても、
判断の中身をすぐ確認できます。

| シナリオ | 見えるもの |
|---|---|
| 1点だけ足りない人 | 買い足しは1点だけ。候補比較と承認フローへ |
| 買わなくていい人 | 「買い足しは必要ありません」— このサービスの中心的な結果 |
| 重複買いしていた人 | 役割の重複と、今回使わない理由 |
| 予算が足りない人 | 条件に合う商品がないことを説明し、購入を勧めない |

用意しているのは**入力（条件と手持ち）だけ**で、結果は通常とまったく同じ経路から出します。
デモ専用の分岐や、あらかじめ書いた結論は持っていません。

`tests/demo-scenarios.test.ts` が、各シナリオが宣伝どおりの結果を出すことを検証しています。
カタログの `usageTiming` ひとつで「買い足し不要」が「1点提案」に変わるため、
説明文と実際の結果がずれたら検知できるようにしてあります
（実際にこのテストで、夜専用クリームを持たせていた誤りを見つけて直しました）。

### 環境変数

| 変数 | 必須 | 説明 |
|---|---|---|
| `CHIGIRI_EXTERNAL_AI` | 任意 | 既定は有効。`off` で外部送信を完全に停止（利用者が選ぶまでは既定でも送信しない） |
| `CHIGIRI_LLM_DAILY_BUDGET_JPY` | 任意 | 1日のAI利用費の上限（既定 300円）。超えたら決定論的応答へ切り替え |
| `CHIGIRI_LLM_INPUT_JPY_PER_1K` | 任意 | 単価を実請求に合わせる場合に指定（未指定はモデル名からの推定） |
| `CHIGIRI_LLM_OUTPUT_JPY_PER_1K` | 任意 | 同上 |
| `ORCAROUTER_API_KEY` | 任意 | 未設定なら決定論的フォールバックのみで動作 |
| `ORCAROUTER_BASE_URL` | 任意 | 既定 `https://api.orcarouter.com/v1` |
| `ORCAROUTER_MODEL_CHEAP` | 任意 | 既定 `auto`（入力の構造化用） |
| `ORCAROUTER_MODEL_QUALITY` | 任意 | 既定 `auto`（ルーティン説明用） |
| `ORCAROUTER_TIMEOUT_MS` | 任意 | 既定 `20000` |
| `CHIGIRI_HANDOFF_SECRET` | **本番で必須** | 購入引き継ぎトークンの署名鍵（32文字以上）。`openssl rand -hex 32` |

APIキーは**サーバー側でのみ**読み込みます（`NEXT_PUBLIC_` 接頭辞は使いません）。
`server/` 配下は `server-only` でインポートを封じており、クライアントバンドルへの混入をビルド時に検出します。

`CHIGIRI_HANDOFF_SECRET` は、開発時に未設定だと**起動ごとに変わる一時鍵**を自動生成します
（再起動で承認済みリンクが失効するだけで、開発は続行できます）。
`NODE_ENV=production` で未設定の場合は**起動時に失敗**させます。
黙って一時鍵で動かすと、複数インスタンス構成で署名検証が通らず、
「承認したのに遷移できない」が再現性なく起きるためです。

## 9. OrcaRouter の使い方

OrcaRouter を**推論基盤**として組み込んでいます。OpenAI 互換 API として
Route Handler から呼び出し、タスクごとにティアを分けます。

| タスク | ティア | モデル | 出力 |
|---|---|---|---|
| 自然文 → 条件の構造化 | コスト優先 | `auto` | JSON |
| 確定ルーティンの説明 | 品質優先 | `auto` | JSON |
| 疎通確認 | コスト優先 | `auto` | JSON |

`model="auto"` でルーターに選択を委ね、実際に選ばれたモデルを
レスポンスヘッダー（`x-orcarouter-model` 等）またはボディの `model` から取得して
**結果画面に表示**します。

### ティア降格（可用性）

品質優先ティアが一時的に落ちている場合、**コスト優先ティアへ降格して1度だけ再試行**します。
説明が付かないよりは、簡素でも付いたほうが利用者の役に立つためです。

| 失敗の種類 | 挙動 |
|---|---|
| 5xx / 429 / タイムアウト / ネットワーク | 下位ティアで再試行 |
| 4xx（認証・リクエスト誤り） | 再試行しない（同じ結果を繰り返し課金しないため） |
| 両方失敗 | 決定論的な説明へ切り替え。ルーティンの中身は変わらない |

### 疎通確認

**コマンドで確認する**（アプリを起動せずに単体で実行できます）

```bash
ORCAROUTER_API_KEY=sk-... npm run orca:check
# .env.local に書いてあれば環境変数の指定は不要
```

段階ごとに切り分けて表示します。どこで落ちたかがすぐ分かります。

```
1. 認証と接続（GET /models）      … キーが通るか。生成しないので費用ゼロ
2. 生成と構造化出力（POST）        … 応答が返るか、JSON モードが効くか
```

失敗時は原因の候補まで出します（成功なら終了コード 0、失敗なら 1）。

```
✗ HTTP 401
  キーが正しくないか、権限がありません。再発行を確認してください。
  応答: {"error":{"message":"Invalid API key provided", ...}}
```

**画面で確認する**

`/ops` に確認画面があります。押すと固定の短文を1回だけ送り、
接続・認証・モデル選択・構造化出力・費用計算が通ることを確かめます。
利用者のデータは含めないため、この確認のためにプライバシー設定を変える必要がありません。

認証（`/models`）と生成（`/chat/completions`）を分けて実行するため、
**「キーの問題」か「モデル指定や生成の問題」かを切り分けられます。**
提供元が返したエラー本文の冒頭も表示します（運用者向け画面のみ）。

```
POST /api/ops/orcarouter
→ { "reachable": true, "requestedModel": "auto",
    "selectedModel": "gpt-4o-mini", "latencyMs": 22,
    "estimatedTokens": 1500, "estimatedCostJpy": 0.12, "jsonValid": true }
```

### 疎通の検証

`tests/orcarouter-integration.test.ts` は、OpenAI 互換の応答を返すサーバーを
実際に立てて**本物のクライアントを HTTP で通します**（モックの差し替えではありません）。

```
送信形式が OpenAI 互換           messages/model/response_format を検証
Authorization: Bearer <key>      ヘッダーを検証
選択モデルの取得                 ヘッダー優先、無ければ本文の model
使用量からの費用推定             prompt/completion トークンから算出
キャッシュ                       2回目は通信せず、費用 0
HTTP 5xx / 4xx / 空応答          例外にせず失敗として返す
タイムアウト・接続不可           打ち切って失敗として返す
ティア降格                       5xx・429 で下位ティアへ、4xx では再試行しない
```

### AI が担当する範囲

実際にアプリ全体をモック OrcaRouter へ向けて確認した結果です。

```
許可あり : ai.used=true  model=mock/gpt-4o-mini  推定0.12円
           要約と採用理由が AI の文章に変わる
2回目   : cached=true  費用 0
許可なし : ai.used=false  reason=user_local_only  決定論的な文章
→ どちらの場合も、朝のルーティンの商品 ID は完全に一致した
```

**AI が変えるのは文章だけで、結論は変えない**ことを、実行結果で確認しています。

ログに保存するもの／しないもの:

- 保存する: リクエストID・タスク種別・選択モデル・応答時間・成否・JSON検証結果・フォールバック有無・推定トークン数
- 保存しない: 氏名・顔写真・詳細な健康情報・APIキー・**入力本文**

## 10. 安全設計（薬機法・医療境界）

CHIGIRI は美容上の意思決定支援であり、医療サービスではありません。

- **受診勧奨ゲート**: 痛み・腫れ・出血・化膿・水疱・急激な悪化などが入力された場合、
  推薦を**実行せず**医療機関への相談を促します（減点ではなく停止）
- **医療相談の切り分け**: 疾患名・治療・処方に関する相談も推薦を停止します
- **許可表現のホワイトリスト**: 説明文は `data/allowed-claims.json`（化粧品の効能の範囲）から生成。
  医薬部外品の表現は `isQuasiDrug: true` の商品にのみ許可し、違反はカタログ読み込み時に例外化
- **禁止表現の検出**: AI 出力に「治る」「改善します」「絶対安全」「副作用がない」等が含まれた場合、
  その出力を破棄して決定論的説明へ切り替え
- **不確実性の明示**: 成分表示だけからは濃度・処方・使用量が不明であることを常に併記

全画面に次を表示します。

> 本サービスは美容情報の整理を目的としたもので、医療上の診断や治療を提供するものではありません。
> 肌に異常がある場合は使用を中止し、医師や専門家へ相談してください。

### セキュリティ

| 対策 | 実装 |
|---|---|
| オープンリダイレクト | 遷移先はサーバー側カタログ由来のみ。許可リスト＋HTTPS必須＋ポート/認証情報/制御文字を拒否（`url-allowlist.ts`） |
| 承認の偽装 | HMAC-SHA256 署名・10分の有効期限・単回使用（`handoff-token.ts`） |
| ホスト偽装 | 完全一致とドット境界のサブドメインのみ。`endsWith` を使わないため `evil-www.kao.co.jp` は通らない |
| セキュリティヘッダー | CSP（`default-src 'self'` / `connect-src 'self'` / `frame-ancestors 'none'`）、HSTS、`X-Content-Type-Options`、`Permissions-Policy` |
| クリックジャッキング | `frame-ancestors 'none'` ＋ `X-Frame-Options: DENY`（承認ボタンを踏ませない） |
| プロンプト注入 | 役割偽装表記・チャットテンプレートトークン・区切り記号を入口で除去し、データとして囲む（`prompt-safety.ts`） |
| 費用・可用性 | API ごとのレート制限＋本文サイズ上限（`api-guard.ts`） |
| 情報の露出 | Zod の `issues` を返さない。エラー本文に内部構造を含めない |
| ログの秘匿 | コマース監査ログは「何が起きたか」のみ。IP・肌の悩み・アレルギー・手持ち一覧・入力本文を保存しない |
| 決済情報 | アプリは決済を行わず、カード情報を受け取らない・保存しない・LLM へ送らない |

**プロンプト注入が成功しても商品選定は変わりません。** 除外・順位づけ・買い足し判定は
すべて決定論的なコードが行い、LLM 出力は Zod と許可 ID リストで検証してから使うためです。
注入対策は「説明文の乗っ取り」と「構造化出力を壊しての可用性低下」に対する二次防御です。

## 12. 推薦スコア

```
score =
    美容上の関心との一致 × 0.30
  + 肌傾向との一致       × 0.20
  + 手持ち活用への貢献   × 0.20
  + 予算適合             × 0.15
  + 使用感との一致       × 0.10
  + 入手しやすさ         × 0.05
  - 注意要素ペナルティ
```

役割重複ペナルティと工程過多ペナルティは、カテゴリー内順位と使用可能時間が確定する
`routine-builder` 側で適用します。

**関心は優先順位付き**で、先頭ほど重み `1/(i+1)` が大きくなります。
**手持ち商品は予算適合が常に満点**です（追加費用が発生しないため）。

### 工程の時間調整

朝夜それぞれの必要カテゴリーに `critical / recommended / optional` を設定し、
使用可能時間を超える場合は `optional → recommended` の順、
同じ重要度の中ではスコアの低いものから外します。`critical` は外しません。

### ルーティンの複数案

単一の正解を押しつけないため、**標準・時短・じっくり**の3案を出します。

| 案 | 前提 | 意図 |
|---|---|---|
| 標準 | 入力された朝◯分・夜◯分 | 基本の並び |
| 時短 | 最小構成 | 省略しても成立する工程を外し、欠かせない工程だけを残す |
| じっくり | 時間の制約なし | 手持ちで使える工程を組み込み、買い足さずに活用しきる |

3案はいずれも**同じ決定論的ロジック**で、使える時間の前提だけを変えて組み立てています。
工程の優先順位や商品の選び方は変えていないため、案ごとに基準がぶれることがありません。
**中身が同じになった案は出しません**（朝1分と入力された場合、標準と時短は同じ並びになるため）。

あわせて、手持ちから成立する**組み立て方の総数**を数えて表示します。

> 手持ちからは 48通り の組み立て方があります

数え方は「朝・夜それぞれの工程に、その時間帯に使える手持ち商品のどれを充てるか。
省略してよい工程は『使わない』も1通りとして数える」で、画面にもこの定義を書いています。
数字を大きく見せるための概算ではなく、実際に成立する並びの数です。
全部を並べても選べないため、提示するのはスコア順に選んだ数案だけにしています。

### 使用タイミングを考慮した重複解決

役割が重複していても、使用タイミングが違えば両方を活用します。
夜専用クリームと朝夜兼用乳液を持っている場合、夜はクリーム・朝は乳液を使い、
「重複しているから片方を捨てる」という結論にはしません。

## 13. 商品データについて（重要な制約）

`data/products.json` は日本で購入できるコスメ **92点** の手動整備カタログです
（スキンケア 46 / メイク 15 / ヘア 12 / ネイル 10 / ボディ 9）。

**現状、全商品が `sourceCheckedAt: null` / `dataConfidence: "seed"` です。**
これは「公式ブランドサイトとの逐一の突合が未完了」であることを意味します。

- 価格は編集時点の**参考価格**であり、実売価格を保証しません
- `officialUrl` はブランド公式サイトを指しますが、商品ページ単位の検証は未実施です
- UI では該当商品に「公式突合 未完了（参考データ）」バッジを表示し、
  根拠が確認済みであるかのようには表示しません

**本番運用の前に、全92点を公式ページと突合し `sourceCheckedAt` を埋める必要があります。**

### 突合の手順

突合は人が公式ページを開いて確認する作業です。自動では行いません
（開発環境から外部サイトへ到達できないため、確認していないものを
確認したことにしてしまう危険があります）。

```bash
npm run verify:export            # 全92点を CSV に書き出す
npm run verify:export -- demo    # デモで使う7点だけ
npm run verify:export -- haircare  # 分野を絞る
```

`verification/products-worksheet.csv` が出力されます（Git 管理外）。
表計算ソフトで開き、公式ページを見ながら記入欄を埋めてください。

| 列 | 記入内容 |
|---|---|
| 確認結果 | `ok`＝現在の値で正しい / `fix`＝直す / `drop`＝取り扱いをやめる |
| 確認日 | `YYYY-MM-DD`。**必須**。無い行は反映されません |
| 正しい公式URL / 正しい価格 / 正しい内容量 | `fix` のときだけ。空欄の項目は現状維持 |
| 商品写真ファイル名 | `fix` のときだけ。詳細は下の「商品写真」 |

```bash
npm run verify:import -- --dry-run   # 書き込まずに結果だけ見る
npm run verify:import                # data/products.json へ反映
```

反映されるとその商品は `dataConfidence: "official"` になり、UI の
「公式突合 未完了」バッジが消えます。安全側に倒すため:

- **エラーが1件でもあれば、何も書き込まずに終了します**（部分適用を作らない）
- 確認日の無い行、`https` でない URL、数値として読めない価格は反映しません
- `drop` は削除候補として表示するだけで、自動削除はしません
- 新しいホストを指定した場合は `data/merchants.json` への追加も必要です

反映後は `npm test` でカタログの整合性を確認してください。

### 商品写真

ブランドの商品写真は各社の著作物です。**メーカーが配布しているものを、
利用許諾を確認したうえで、自分の配信元に置いたときだけ表示します。**
外部ホストの画像への直リンクはしません（CSP の `img-src` を `'self' data:`
に保つため、そもそも読み込めません）。商品の外観を推測した画像も作りません。

登録の手順:

1. メーカーの配布素材を、許諾を確認したうえで用意する
2. `public/products/<商品id>.jpg` として置く（`png` / `webp` も可）
3. ワークシートの「商品写真ファイル名」に置いたファイル名を書き、確認結果を `fix` にする
4. `npm run verify:import`

`verify:import` は、指定されたファイルが `public/products/` に実在するかを
確認します。置かれていないファイル名を指した行はエラーになり、
読み込めない画像を指したまま「確認済み」にはなりません。

**写真が未登録のあいだの表示**

写真の代わりに、役割（ポンプ・チューブ・ジャー等）とブランドから決まる
線画を出します。同じ商品には必ず同じ図案が出るので、一覧やルーティンで
商品を見分ける手がかりになります。

これは商品の写真ではありません。実際の容器を再現したものでもないため、
詳細画面では「写真未登録」と明記し、図案であることを説明しています。

図案の仕様は `domain/recommendation/product-image.ts`、
描画は `components/ProductThumb.tsx` です。写真を登録すると、
その商品だけ自動的に写真の表示へ切り替わります。

## 14. 品質基準の達成状況

| 受け入れ条件 | 状態 | 担保方法 |
|---|---|---|
| カタログ外の商品をAIが推薦しない | ✅ | 許可IDリスト照合＋不一致で出力破棄（`explanation.ts`） |
| 明示的な除外条件に違反しない | ✅ | ハードフィルタ＋テスト S13/S14 |
| 同じ入力から同じ結果になる | ✅ | 純関数スコア＋一意なタイブレーク（テスト S26） |
| AIが失敗してもルーティンを表示できる | ✅ | 決定論パイプラインが独立（`skipLlm` / キー未設定で検証） |
| 公式URLのない商品を根拠ありとしない | ✅ | `sourceCheckedAt: null` を未検証として表示 |
| 全API入力・AI出力をZodで検証 | ✅ | 入力・出力・LLM応答すべて |
| APIキーがクライアントバンドルに含まれない | ✅ | `server-only` ＋ ビルド成果物の走査で確認 |
| スマホ幅で横スクロールが発生しない | ✅ | `overflow-x: hidden` ＋ モバイルファースト設計 |
| 20件以上のテストシナリオ | ✅ | 251ケース |
| 手持ちだけで足りる場合に購入を提案しない | ✅ | `NO_PURCHASE_NEEDED` を成功終端として実装 |
| 最大買い足し数・予算を超えない | ✅ | 候補生成時と承認直前の二重チェック（`over_budget`） |
| 採用・不採用の両方の理由を表示 | ✅ | 全候補に `notChosenReason` を必須化（テストで検証） |
| 承認なしで外部遷移・注文処理をしない | ✅ | 状態機械が `userInitiated` を要求＋署名付きトークン |
| 外部URLを許可リストで検証 | ✅ | 発行時と遷移時の二重検証（`url-allowlist.ts`） |
| 既定設定で外部へ送信しない | ✅ | `fetch` が呼ばれないことをテストで検証（`ai-policy.test.ts`） |
| 会話履歴を残し、開き直せる | ✅ | 端末内保存。条件と生成済みルーティンまで復元 |

## 15. デモの流れ（3分）

1. `/chat` で「混合肌で毛穴と乾燥が気になります。予算は3000円くらい」と入力
2. 「手持ち」から6点を選択（洗顔1・化粧水2・美容液1・乳液2、**日焼け止めなし**）
3. 「この条件で組み立てる」
4. → **手持ち6商品のうち5商品を活用。新しく必要なのは日焼け止め1点だけ。約6,644円の購入を回避**
5. 朝・夜ルーティンがタイムラインで表示される。
   **「標準／時短／じっくり」**を切り替えると工程数と手持ち活用点数が変わる。
   「手持ちからは48通りの組み立て方があります」で、選んだ範囲を開示する
6. 化粧水の役割が重複していることと、その1点を今回使わない理由が表示される
7. 買い足し候補1点＋次点候補＋公式リンク
8. 「なぜこれを選んだか」を開くと採用理由、根拠パネルに公式URLと OrcaRouter の選択モデル
9. 予算を1000円に変更 → 再計算で提案商品が変わる
10. **「候補を比べて決める」** → 候補3件の比較。選ばなかった理由が候補ごとに出る
11. **「予算を715円に下げると提案が変わります」** — 結論の境目を提示（反実仮想）
12. **承認画面** — 販売者・送料の扱い・在庫確認時刻・返品条件・**未確認項目**を明示。
    未確認項目を了解するまで承認ボタンは押せない
13. **「今回は買わない」** を承認と同じ大きさで置く → 選ぶと見送り額が記録される
14. 承認した場合のみ、署名付き・10分・単回使用のリンクが発行され、販売サイトへ 303 遷移
15. 「AIがたどった手順」を開くと、どの状態で止まっていたかが見える
16. 「商品を売るAIではなく、必要性を判断してから買うAI」

## 16. MVPで実装していないもの

顔写真による肌診断／医療的な診断／治療方法の提案／自動スクレイピング／
1000件以上の商品DB／**アプリ内決済・自律購入・カード情報の保存**／本格的な認証／
SNS・コミュニティ／ネイティブアプリ／ベクトルDB／ファインチューニング／
リアルタイム在庫・価格取得／気象データ連携／プッシュ通知／アフィリエイト優先表示

### 現時点の制約（本番化の前に必要なこと）

| 項目 | 現状 | 必要な対応 |
|---|---|---|
| 在庫・価格・送料 | すべて未確認として表示 | 販売者APIまたはACP/UCP接続で実データを取得 |
| 商品カタログ | 92点・`sourceCheckedAt: null` | `npm run verify:export` → 記入 → `npm run verify:import` で `dataConfidence: "official"` へ |
| レート制限 | プロセス内メモリ | 複数インスタンスでは Redis 等の共有ストアへ |
| 使用済みトークン | プロセス内メモリ | 同上（現状は再起動で使用済み記録が消える） |
| 監査ログ | 標準出力＋直近200件 | 永続化と保持期間ポリシーの設定 |
| 美容グラフ | 端末内のみ | サーバー同期する場合は同意管理・削除権の実装が別途必要 |

`CommerceAdapter` インターフェースを挟んであるため、
実EC接続や ACP / UCP への差し替えは `static-adapter.ts` の置き換えで済みます。
UI・状態機械・承認フローは変更不要です。
